# 认知工效：让代码执行路径与状态变化可推演

> 核心目标：代码是人与协作者（包括 AI 协作者）理解系统行为的媒介。白盒代码必须最大限度降低维护者的“工作记忆负荷”，使人在无需借助脑内单步调试的情况下，仅凭静态阅读即可推演出执行路径与状态变更。

---

## 1. 为什么关注认知工效

软件维护的大部分时间并不在“敲击键盘”，而在“理解上下文”：
- 跟踪一个入参穿透了多少层未做任何加工的函数？
- 观察一个对象在传递给第三方辅助方法后，内部属性是否被暗中更改？
- 面对层层嵌套的 `if-else` 分支，当前这行代码究竟在满足哪些前置条件下才会触发？

当上下文跨度过大、中间层级过多或副作用隐蔽时，开发者和审查者的认知容量会被迅速耗尽，从而导致盲区与脆弱的改动。

---

## 2. 核心支柱一：执行路径可推演

### 2.1 扁平化与提早返回 (Early Return)
嵌套的分支语句（特别是嵌套超过 3 层的结构）会强制阅读者在脑海中维护一个深度的栈结构。
- **卫语句 (Guard Clauses)**：在函数顶部对不合法、提前结束或边缘条件直接做处理并 `return` 或 `throw`。
- **主干通道 (Happy Path)**：将主要业务逻辑保持在最外层的平坦缩进中。
- **嵌套深度信号**：嵌套深度 $>3$ 视为重要的**审查信号 (Review Signal)**，提示此处的逻辑抽象或分支拆解需要重构，但并非机械式的一票否决（如某些固有的深度树遍历算法）。

### 2.2 消除幽灵抽象 (Eliminate Ghost Abstractions)
许多代码充斥着如下形态的“伪抽象”：
```typescript
// 典型幽灵抽象：仅作简单透传，没有任何防腐、契约转换或错误处理职责
function getUserData(userId: string) {
  return fetchUserById(userId);
}
```
**判定边界与审阅标准**：
- **按职责判断**：不以“仅被调用一次”或“代码行数少”自动判定为错误。
- **何为有效抽象**：提供领域边界防腐（如将外部 HTTP DTO 转换为内部 Entity）、提供错误捕获重试逻辑、或者为复杂算法提供单一职责的隔离单元。
- **何为幽灵抽象**：既不转换数据契约、也不隔离底层技术细节、也不具备独立单元测试价值，仅仅是增加了一层跳转命名。幽灵抽象应当果断内联（Inline）。

---

## 3. 核心支柱二：状态变化可定位

### 3.1 行为就近编排 (Behavior Colocation)
将紧密相关的状态、衍生计算与修改动作组织在物理相近的上下文（同一文件或同级特性包）中。
- 反对机械式地按技术名词拆分（如把只在一个模块使用的 5 行帮助函数放到全局 `utils/`，或把一对互斥状态拆在两个完全隔离的全局 Store 中）。
- 就近性使阅读者在同一屏内即可看到状态定义及其所有可能的变化路径。

### 3.2 消除未声明的共享修改 (No Undeclared Mutation)
- 函数如果在入参或全局共享对象上执行就地修改（in-place mutation），调用方将无法从调用签名上觉察此副作用。
- 遵循不可变数据流更新原则；若出于极致性能考虑确实需要原地修改，必须在函数命名与类型契约上显式声明（例如 `normalizeInPlace(buffer)`）。

### 3.3 命名契约与副作用对齐
- `get...` / `is...` / `calculate...` / `find...` 等具有查询语义的函数，必须保证是无副作用的纯函数（Pure Functions）。
- 绝不允许在只读命名的函数内部暗中触发数据写入、状态清空或网络请求。

---

## 4. 核心支柱三：领域概念显式化

- 拒绝代码中的“魔数 (Magic Numbers)”与“魔术字符串”。
- 将具有业务含义的判定条件提炼为具名常量或明确的枚举/字面量类型。
- 避免使用组合布尔变量模拟复杂流程，采用显式判别联合（Discriminated Union）或有限状态机表达业务生命周期。
